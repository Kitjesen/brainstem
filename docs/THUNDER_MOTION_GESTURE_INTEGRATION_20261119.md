# Thunder 平地／楼梯与动作 API 接入说明

## 当前共同基线

运动槽位接口已由 PR #4 合并；机载动作库接口已由 PR #6 合并，当前共同源码基线为 `31af705b0d588b71b7a157b71de2509bee102f4a`。动作改动是在槽位版本上继续开发的，不需要另开一套控制电机的服务。

二号机 2026-11-19 只读核查：`brainstem.service` 运行该动作版本，`GetProfile` 同时返回可用的 `flat`、`stairs`，`ListGestures` 返回21个机载动作。此结果证明接口和目录可读，不证明所有动作已获实机验证。

## App 调用合同

| 用途 | RPC | 参数与行为 |
| --- | --- | --- |
| 获取运动槽位 | `GetProfile` | 读取 `mode_capabilities` 与 `active_mode_id` |
| 选择平地 | `SwitchProfile` | `name = "flat"`，模型绑定由机器狗端配置 |
| 选择楼梯 | `SwitchProfile` | `name = "stairs"`，模型绑定由机器狗端配置 |
| 获取一次动作目录 | `ListGestures` | 获取名称、描述与时长，不硬编码轨迹 |
| 播放一次动作 | `PlayGesture` | `GestureRequest.name` 使用目录中的名称 |
| 正常站起／趴下 | `StandUp`／`SitDown` | 继续使用正式姿态流程 |

运动策略是持续控制；手势是有起止的一次动作。App 保留两类入口，不把动作名称塞入 `flat`／`stairs` 槽位，不把模型文件名写到App。替换平地或楼梯模型只需更新狗端绑定。

`stand_up`、`wake_stand`、`lie_down` 等目录项是普通片段，不能因为名字相似就代替正式 `StandUp`／`SitDown`。

## 执行与状态约束

- 复用现有连接、控制权、状态与错误处理；查询目录不会取得控制权或使能。
- 从 `GROUNDED` 播放 `start_pose=standing` 的动作，服务可能先执行正式站起再播放；App必须让用户知道这次请求可能包含站起。
- 行走、姿态转换、已有动作执行、RobotRecovery、电机未使能、严重故障或关节不健康时，动作请求可能被拒绝；把服务真实原因反馈给用户。
- 动作播放及其前置站起过程中，策略切换会被拒绝。不要并发发送动作、切换和摇杆输入，也不要失败后自动重放动作。
- 多数动作结束为 `STANDING`；坐姿和趴姿片段按服务报告结束在 `GROUNDED`。使用状态反馈确认结束，不只依赖目录时长。
- 目录说明目前只含名称、描述、时长，App不能从这些字段推断动作起止姿态或认证等级。

## 融合与验证步骤

1. 服务端以共同基线继续开发，保留已验证CAN腿部映射、遥控器、模型绑定、PD及保护参数，避免并行启动两个电机控制服务。
2. App在现有双槽控制上接入动作查询与播放；实现前先核对同事现有分支，避免覆盖相同功能。
3. 机载动作使用绝对关节目标。核对选中profile的站姿、动作起止姿态、关节限位、轮子目标以及动作实际使用的控制增益。
4. 在MuJoCo验证动作开始／结束衔接、动作期间策略切换拒绝、回到站立后恢复摇杆、断线与中止路径，再做有限动作的现场验收。
5. 图传沿用独立媒体链路，合入同一App时同时保留动作入口和策略槽位，不将视频接通当成运动功能验收。

## 验证边界

本说明整理的是接口合同与只读检查结果。本次没有调用 `PlayGesture`、`StandUp`、`SitDown`、`SwitchProfile` 或电机使能接口，没有部署新的运行时。21个动作逐项仿真／实机验证、动作PD与实际站姿衔接、App动作入口接入仍需独立验证。
